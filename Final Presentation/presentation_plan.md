**標題**：爬蟲不只是「下載資料」——我們踩了什麼雷

**問題 1 ／ 發現延遲：10,238 支影片，只有 202 支能用**

```
收到的影片                    30 min 後才被發現
發布時 ─────────────┬──────────────▶ 爬蟲才看到
                  0–3h 早期窗口
                  (已過，無法重建)
```
- 舊策略（Explore / Channel）抓到的影片平均已過 30 分鐘，0–3h 早期資料全部缺失
- 10,238 支影片，只有 **202 支**（1.97%）有完整的 0–3h 資料可供分類訓練
- **解法**：改用 `fresh_search`，過濾「上傳 ≤5 分鐘」的影片；只收真正剛發布的影片

---

**問題 2 ／ YouTube API 持續改版，三個 endpoint 失效**

| 功能 | 原本 | 壞掉原因 | 解法 |
|---|---|---|---|
| 熱門影片 | `/feed/trending` | 2025 年下架 | 改 Explore 分類頁 |
| 頻道新片 | Atom RSS | 回傳 404 | 改 InnerTube browse API |
| 留言內文 | `commentRenderer` | 搬到 ViewModel mutations | 加 `_extract_mutations()` 解析 |

- Shorts 首頁每次只顯示一支影片（無法爬清單）→ 改用搜尋 + `sp=EgQQARgD` 短片過濾器

---

**問題 3 ／ 雙 Scheduler 互毀 JSON（競爭寫入）**

```
Process A ──▶ write videos_static.tmp ──▶ rename to .json ──▶ ✓
Process B ──────────▶ write videos_static.tmp  ←── 同時截斷同一個 tmp 檔
結果：檔案前半是 A 的、後半是 B 的 → JSON parse error，177 筆資料損毀
```
- 根因：cron job 健康檢查偶發性開了第二個 Scheduler，兩個 process 同時寫同一個 `videos_static.tmp`
- **解法**：tmp 檔名加入 PID（`videos_static.{PID}.tmp`）；寫入不再互相覆蓋
- 損毀恢復：用 `raw_decode()` 拆解前段有效 JSON，救回 2,081 筆

---

**問題 4 ／ `_sleep` 負數 Race Condition → 10 小時停擺**

```python
# 舊程式碼（有 race）
while time.monotonic() < end:          # check 時未過期
    time.sleep(end - time.monotonic())  # 計算時已過期 → 負數 → crash

# 修復後
while True:
    remaining = end - time.monotonic()
    if remaining <= 0: break
    time.sleep(min(0.5, remaining))
```
- 一行 race condition 造成 scheduler crash，無人發現直到 10 小時後人工檢查
- 那 10 小時內的所有新影片，0–3h 早期資料全部遺失，無法用於分類訓練

---

**講述要點**：
- 「這四個問題是同時期發生的，處理這些比跑模型花了更多時間」
- **發現延遲**是最值得強調的：「不是爬蟲技術問題，是策略問題」——舊策略根本在爬錯的資料
- API 失效可以一句帶過：「YouTube 沒有公開 API，我們全靠逆向工程，所以維護成本高」
- Race condition 是工程趣味點，可以拿出來說但不用深入

### Slide 6 — 爆紅標籤定義（1 min）

**標題**：「爆紅」不只是觀看數——要考慮頻道規模

**公式框**：
```
effective_sub  = max(subscriber_count, 1,000)
threshold      = max(
                   10,000  (Shorts) / 2,000 (長影片),
                   2 × effective_sub
                 )
is_viral       = views_48h ≥ threshold
```

**右側對比表**（直觀說明）：
| 訂閱數 | 類型 | 爆紅門檻 |
|---:|---|---:|
| 500 | Shorts | 10,000 |
| 8,000 | 長影片 | 16,000 |
| 100,000 | 任意 | 200,000 |

**附圖**：`fig03_viral_rate_by_type.png`

**講述要點**：
- 「對 100 萬訂閱的頻道，10 萬觀看不算爆紅；對小頻道，10 萬觀看絕對算」
- 這個定義考慮了公平性

### Slide 9 — [核心發現 1] 最大跳躍：A → B（1.5 min）⭐

**標題**：加入「早期流量」特徵，F1 從 0.33 跳到 0.73

**主視覺**：`fig13_ablation_classification.png`（Ablation 長條圖）

**數字強調**：
```
LightGBM   A → B
F1:       0.327 → 0.731   (+0.40  ↑ 124%)
AUC:      0.733 → 0.937   (+0.20)
```

**右側說明框**：
> Group A 只有靜態特徵（訂閱數、長度…）
> Group B 加入 views_3h、成長率、互動率…
> → **早期觀看速度是爆紅預測的核心資訊**

**附圖**：`fig07_views3h_vs_viral.png`（viral vs non-viral boxplot）

**講述要點**：
- 「這個結果印證了文獻：早期 1–3 小時的動能是最關鍵的信號」
- 「靜態特徵本身（訂閱數）不足以預測，必須結合早期反應」

### Slide 10 — [核心發現 2] SHAP 解釋（1 min）⭐

**標題**：最關鍵特徵：頻道訂閱數，差距遠超所有其他特徵

**主視覺**：`fig06_shap_importance.png`

**右側解讀框**：
```
#1  log_subscriber_count  SHAP = 2.109  ← 比第 2 名高 2.7 倍
#2  views_3h              SHAP = 0.770
#3  view_delta_1h_3h      SHAP = 0.683

```

**一句話洞見**：
> 「你 3 小時內能爆紅，最重要的原因是你的頻道本來就有受眾。
> 但你的早期成長速度，決定了你有沒有超越受眾期待。」

**講述要點**：
- 「SHAP=2.109 vs 0.770，差了 2.7 倍——這不是微幅差距，是數量級差異」
- 連結到直覺：一個 100 萬訂閱頻道的任何影片，天生就有更多曝光機會

## 四、重點講述策略

### 什麼要詳細說
- **Slide 5（分組切分）**：這是本專題最有工程深度的設計決策，不是課本上的，要給聽眾充分時間理解「問題 → 解法」
- **Slide 9（A→B 跳躍）**：這是最直觀、最戲劇化的結果，配合 boxplot 說明為什麼早期流量如此重要
- **Slide 10（SHAP）**：2.109 vs 0.770 的數字差距非常震撼，讓圖說話，加上直覺解釋

### 什麼要快速帶過
- 技術細節（防洩漏規範、checkpoint 容許誤差）——放在 REPORT 就好
- 超參數設定——答問題時才講
- 迴歸任務——整個專題的核心是分類，迴歸是補充

### 如何處理 LSTM 結果差的問題
- 不要迴避，直接解釋：「LSTM 沒有訂閱數這個最強特徵，序列只看流量三個數字」
- 這反而是個 insight：「如果 LSTM 加入靜態特徵，應該會好很多」

### 如何處理問答
預期問題：
1. **為什麼不用更多的模型（XGBoost、Random Forest）？**
   → 「我們聚焦在 Ablation Study 的設計，而不是廣泛比較所有模型。LightGBM 是 GBDT 家族的代表。」
2. **C 系列的 NaN 填 0 會不會造成偏差？**
   → 「是的，這是主要限制之一。0 代表中性，可能不準確。若覆蓋率提升，改善幅度應更大。」
3. **Stacking 為什麼比 LightGBM 單模差？**
   → 「LSTM OOF 的機率品質很差（AUC=0.590），拖累了融合效果。」
